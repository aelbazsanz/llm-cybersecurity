# LLM01:2025 Audit Laboratory

## Overview

This laboratory provides an audit workflow for the evidence generated by the LLM01:2025 Direct Prompt Injection attack laboratory.

The objective is to transform raw experiment logs into structured security findings and map those findings to relevant security frameworks, including:

* OWASP Top 10 for LLM Applications
* MITRE ATLAS

The audit laboratory does not perform attacks itself. Instead, it consumes the JSONL evidence generated by the attack laboratories.

```text
Attack Laboratory
        │
        │ JSONL evidence
        ▼
┌──────────────────────┐
│   LLM01 Audit Lab    │
├──────────────────────┤
│ Evidence ingestion   │
│ Experiment analysis  │
│ Finding generation   │
│ Framework mapping    │
│ Report generation    │
└──────────┬───────────┘
           │
           ▼
     Local audit report
```

## Scope

The initial scope is the audit of direct prompt injection experiments from:

```text
labs/lab01-llm01-direct-prompt-injection/
```

The audit workflow is designed to support multiple experiments, runs, sessions, turns, and models.

The number of experiments is not hard-coded. The audit tool discovers the available JSONL evidence at runtime.

## Evidence Model

The attack laboratory records one JSON object per interaction in JSONL format.

The audit workflow preserves the following traceability:

```text
Experiment
    │
    ├── Run
    │     └── Session
    │           └── Interaction
    │
    └── Run
          └── Session
                └── Interaction
```

This allows an audit finding to be traced back to the original experiment and individual model interaction.

The current evidence records include identifiers such as:

* `lab_id`
* `experiment_id`
* `experiment_name`
* `run_id`
* `session_id`
* `turn`
* `model`
* `attack_type`
* `technique`
* `success`
* `success_reason`
* `detection_method`

## Repository Artifacts

Generated execution data is intentionally not committed to the repository.

### Versioned

The repository contains:

* Audit source code
* Framework mappings
* Documentation
* Configuration required to reproduce the audit

### Local only

The following artifacts are generated locally and are excluded from Git:

```text
logs/
evidence/
reports/
```

This is intentional.

The repository provides the **audit methodology and tooling**, while each user generates their own evidence and reports from their own experiments.

This avoids committing model-specific, environment-specific, or potentially sensitive experiment output.

## Running the Audit

The audit tool receives the directory containing the attack laboratory JSONL evidence.

Example:

```bash
uv run lab01-audit \
  --evidence ../lab01-llm01-direct-prompt-injection/logs
```

The audit tool discovers the available evidence automatically.

For example, an execution may report:

```text
LLM01:2025 Audit
========================================

Evidence directory: ../lab01-llm01-direct-prompt-injection/logs

Interactions: 19
Experiments:  11
Runs:         12
Sessions:     12
Successful:   6
Failed:       13

Models:
  - llama-guard3:8b
  - phi4-mini:latest
  - qwen3:8b
```

The exact results depend on the experiments and models executed by the user.

## Audit Workflow

The audit implementation is intentionally separated into several stages.

```text
JSONL evidence
      │
      ▼
   loader.py
      │
      ▼
   findings.py
      │
      ▼
   mappings.py
      │
      ▼
    report.py
      │
      ▼
 Audit report
```

### Evidence Loader

`loader.py` is responsible for reading and validating the JSONL evidence.

It answers:

> What evidence was generated?

It does not make security conclusions.

### Findings

`findings.py` will transform the observed evidence into structured security findings.

It answers:

> What security issue is supported by the evidence?

A finding will retain references to the experiments and interactions that support it.

### Framework Mappings

`mappings.py` will associate findings with relevant security frameworks.

The primary frameworks for this laboratory are:

* OWASP Top 10 for LLM Applications
* MITRE ATLAS

Mappings will only be made when supported by the evidence. The audit process will not force a framework mapping when no direct relationship exists.

### Reporting

`report.py` will generate human-readable audit reports from the structured findings.

Reports are generated locally and are not intended to be committed to the repository.

## Initial Framework Scope

The primary vulnerability for this laboratory is:

```text
OWASP LLM01:2025
Prompt Injection
```

Direct prompt injection is the primary attack class investigated by the corresponding attack laboratory.

Where the evidence demonstrates disclosure of protected or sensitive information, the resulting impact may additionally be considered in relation to:

```text
OWASP LLM02:2025
Sensitive Information Disclosure
```

The distinction between vulnerability and impact is intentional:

```text
Prompt Injection
       │
       ▼
Model behavior manipulation
       │
       ▼
Protected information disclosure
```

For MITRE ATLAS, the audit will evaluate relevant mappings such as:

```text
AML.T0051.000
LLM Prompt Injection: Direct
```

Other ATLAS techniques, such as direct LLM jailbreak techniques, will only be mapped when the observed evidence supports the relationship.

## Finding Traceability

A finding should be traceable back to the evidence that produced it.

The intended relationship is:

```text
Finding
   │
   ├── Experiment ID
   ├── Run ID
   ├── Session ID
   ├── Turn
   ├── Model
   │
   ├── OWASP mapping
   ├── MITRE ATLAS mapping
   │
   ├── Impact
   ├── Detection
   ├── Mitigation
   └── Validation
```

This allows the audit report to answer not only:

> What vulnerability was found?

but also:

> Which experiment demonstrated it?

> Which model was affected?

> Which interaction produced the evidence?

> Which framework mappings apply?

> Was the mitigation subsequently validated?

## Reproducibility

The audit laboratory is designed to produce reproducible reports from locally generated evidence.

A typical workflow is:

```text
1. Run attack experiments
        │
        ▼
2. JSONL evidence is generated
        │
        ▼
3. Run the audit laboratory
        │
        ▼
4. Findings are generated
        │
        ▼
5. Framework mappings are applied
        │
        ▼
6. Local audit report is generated
```

Different users may therefore obtain different reports depending on:

* Models tested
* Experiments executed
* Prompt variations
* Model versions
* Number of interactions
* Observed model behavior

The repository intentionally does not include a fixed experiment result set.

## Design Principles

### Evidence before conclusions

The audit process starts from observed evidence rather than predefined conclusions.

### Traceability

Every finding should be traceable to the underlying experiment and interaction.

### No forced mappings

A finding should only be mapped to OWASP, MITRE ATLAS, or another framework when the relationship is justified.

### Separation of attack and audit

Attack laboratories generate evidence.

The audit laboratory analyzes that evidence.

This separation allows the same audit methodology to be reused across future laboratories.

### Reproducibility

Users should be able to execute the attack laboratories, generate their own evidence, and reproduce the audit process locally.

## Future Work

Planned extensions include:

* Automatic experiment aggregation
* Structured security findings
* OWASP mappings

* Impact classification
* Mitigation recommendations
* Mitigation validation through attack replay

* Support for additional LLM security laboratories
* Additional framework mappings where appropriate, such as NIST AI RMF, CWE, CAPEC, and relevant NIST adversarial ML resources

The project will avoid forcing mappings to frameworks when no meaningful relationship exists.
